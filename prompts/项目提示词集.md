> 配套说明：本文档是给 **Agent 型编程工具（DeepSeek Harness / Claude Code / Cursor 类）** 使用的一套分阶段提示词。
> 每个提示词都是**自包含**的独立任务指令：把「背景上下文、明确目标、具体步骤、输入输出、约束、验收标准」完整写清，
> 由 Agent 一次性执行。建议顺序：B(逆向)→C(suburb)→A(脚手架)→D(地图)→E(解析)→F(招聘展示)→G(AI 筛选)→H(集成)。

## 🌍 全局项目上下文（每个提示词都要随附或引用）

```
项目是一个“澳大利亚找工作”Web 应用。用户交互流程：
(a) 地图选址：在地图上点选澳洲的某个位置。
(b) 地理位置解析：把用户选的位置（地名/坐标）交给大模型，大模型结合提前抓取的澳洲
    suburb(城区)接口数据，解析出用户附近/所在的城市和 suburb。
(c) 招聘信息获取：调用 YEEYI 亿忆 平台(yeeyi.com)的求职招聘接口，拉取职位并在 Web 页面展示，
    默认过滤掉要求 PR(永久居留)的职位。
(d) AI 筛选总结：把抓到的结构化职位数据继续交给 AI，通过 Chatbot 式自然语言交互，
    让 AI 挑选并总结出合适的企业/职位并推荐给用户。

技术栈（全局约束，所有阶段都要遵守）：
- Web 框架：Next.js（App Router）
- AI 与 Web 交互：Copilot Kit（https://copilotkit.ai ，React 组件，用于 AI 聊天/调用）
- 页面状态管理：Zustand
- 样式：Tailwind CSS
- 运行环境：面向 DeepSeek Harness / Agent 环境的可执行项目

通用约定：
- 所有代码用 TypeScript。
- 所有与外部平台的对接都做成可配置项（环境变量 .env.local 管理），不硬编码密钥。
- 每个功能模块提供清晰目录划分，注释说明职责。
- 每次改动后运行类型检查 / lint / build，确保可编译通过。
```

## 🧩 Prompt B — YEEYI 求职接口逆向与接口文档化（核心前置）

```
【全局上下文】<粘贴/引用上方的“全局项目上下文”>

【任务目标】
对 YEEYI(亿忆 / yeeyi.com) 平台的求职招聘接口做逆向分析：找到真实的职位数据接口，
抓取并分析它的请求方式、URL、请求头、入参、出参结构，输出一份完整、可落地的“接口文档”，
供后续开发阶段直接编码对接。这一步只产出文档和接口调试脚本，不改业务前端。

【背景说明】
我们无法预先拿到 YEEYI 的开放 API 文档，需要通过对平台网站/App 的网络请求进行抓取分析。
用户需求的接口用途：按位置/surburb/关键词 拉取职位列表，过滤掉要求 PR 的职位。

【具体步骤】
1. 调研方式确定：优先尝试直接访问 yeeyi.com 的招聘频道页面，识别其前端请求。说明抓包手段
   （浏览器 DevTools Network / 代码内直接 fetch 探活）并挑选网络可达、能复现的那一种。
2. 定位真实数据接口：在页面交互（搜索职位、翻页、按分类筛选）时观察网络请求，定位返回
   JSON 的职位列表接口（可能是 fapi / wapi / api 下的某个路径）。给出该接口的完整 URL 与请求方法。
3. 分析并记录请求详情：
   - 完整 URL、method、headers（是否需要 cookie / token / User-Agent / referer / 签名 / 时间戳）。
   - 全部入参（query 或 body JSON）：地区/城市、suburb、关键词、分类、薪资、是否 PR、
     分页(page/pageSize)、排序、是否预请求(gateway 类)等，能识别的字段都列出来。
   - 入参来源：哪些来自页面直填，哪些来自前置接口返回（如地区 code）。
4. 分析出参结构：用真实返回样例，画出职位对象的核心字段树（职位 id、标题、公司名、薪资、
   工作类型、地区/suburb、技能要求、是否要求 PR、发布时间、url、公司信息等），标注字段类型与可空性。
5. 落地文档：写出 `docs/yeeyi-api.md`，包含：接口清单、每个接口的 请求样例(含真实 URL)+响应样例(脱敏)+
   字段字典+用到时的示例代码(fetch/axios)。同时把对应 TypeScript 类型写到 `types/yeeyi.ts`。
6. 写一个独立的调试脚本 `scripts/yeeyi-probe.ts`（Node/tsx 均可跑），能按关键词+城市调一次接口，
   把原始响应打印出来，用于验证文档正确性。

【约束】
- 逆向阶段只做读取类请求，不做危险写操作；遵守平台规则，仅少量、低频请求用于分析。
- 若接口需要签名/登录，必须明确指出，并给出“如何获得/是否可绕过”的结论与备选方案
  （例如：尝试无鉴权直连、说明需登录后带 cookie 的方式）。
- 文档要能被后续开发阶段直接当作编码依据（字段名、类型、入参默认值都要准确）。

【验收标准】
- `docs/yeeyi-api.md` 存在且覆盖：接口 URL、method、headers、全部入参、出参 JSON 结构、字段字典、
  示例代码、反爬注意事项。
- `types/yeeyi.ts` 与文档一致。
- `scripts/yeeyi-probe.ts` 能真实跑通（或给出被反爬时的明确处理结论和可执行的替代路径）。
- 明确回答：能否拿到“是否要求 PR”这个字段；拿不到则给出可用的替代判断思路（关键词匹配等）。
```

## 🧩 Prompt C — 澳洲 Suburb 数据准备与接口化

```
【全局上下文】<粘贴/引用上方的“全局项目上下文”>

【任务目标】
准备一份“澳洲城市 + suburb(城区)”的静态数据，并把关键词→经纬度→suburb 的解析能力准备好，
让后续“大模型解析用户位置 → 找到附近 suburb → 查职位”这一环有数据基础。

【背景说明】
用户在地图点选位置后，会交给 LLM 结合“ suburb 接口数据”找附近城区。因此我们需要一份覆盖
澳洲主要城市及其 suburb 的清单，必要时含坐标范围，供 LLM 参考定位。

【具体步骤】
1. 数据来源：说明采用哪种方式落地 suburb 清单——
   - 优先：找一个可公开获取的澳洲 suburb 数据源（如澳洲政府/开源数据、经评审可用的公开数据集），
     说明其结构、覆盖范围、更新频率与授权。
   - 备选：手工整理一份主要城市（悉尼/墨尔本/布里斯班/珀斯/阿德莱德等）及其典型 suburb 的核心清单，
     明确范围边界（覆盖到 suburb 级别即可，不强求全量）。
2. 结构化：把 suburb 数据整理成 `data/suburbs.json`（或 TS 模块），字段至少包含：
   州/城市/city、suburb 名、经纬度或边界框，有则加邮编。
3. “位置→suburb 匹配”辅助能力：写 `lib/geocode.ts`，提供按关键词/坐标在 suburb 数据里模糊匹配的函数
   （支持中英文 suburb 名、拼写近似），并声明该函数会被大模型解析流程复用。
4. 若挑选的是 LLM 解析方案，则在文档 `docs/suburb-data.md` 里写明：
   “给出用户点选地名 → LLM 用这份 suburb 数据推断 主城市 + 候选 suburb”的输入输出约定和示例。

【约束】
- suburb 数据来源必须开源/可授权或自行整理，不许用受版权限制的私有数据。
- 让这份数据可被 LLM 直接拿来推理（体积适中、结构清晰）。

【验收标准】
- `data/suburbs.json` 存在且结构完备，至少覆盖主要首府城市及常见 suburb。
- `lib/geocode.ts` 提供可调用的匹配函数并有简单测试/样例。
- `docs/suburb-data.md` 说明数据来源、字段含义、LLM 解析的输入输出约定。
```

## 🧩 Prompt E — 地理位置解析（大模型 + suburb 数据 → 确定城市/suburb）

```
【全局上下文】<粘贴/引用上方的“全局项目上下文”>

【任务目标】
把地图选中的位置交给大模型，结合提前准备的澳洲 suburb 数据，解析出“用户所在的城市 +
附近物理上的 suburb（作为职位筛选条件）”，输出结构化结果并存入 Zustand。

【具体步骤】
1. 在后端/API 路由实现一个“位置解析”接口（Next.js Route Handler，如 `app/api/resolve-location/route.ts`）：
   入参 = 用户在 D 阶段拿到的 {lat, lng, placeName}。
2. 后端把该入参 + 一段精炼的澳洲 suburb 数据（来自 Prompt C，控制 token 量，只喂相关城市片段）
   一并构造 prompt 发给大模型（接入方式见 Prompt G 的 CopilotKit 后端，或先用一个可配置的 LLM 客户端）。
3. 定义清晰 prompt 模板与输出约束：让 LLM 返回 JSON——
   { mainCity: string, country: "Australia", suburbs: string[] , confidence: number,
     reasoning: string }。要求 suburbs 是物理上接近选中点、且可用于职位筛选的城区名，并给出理由。
4. 做可靠的输出解析：对 LLM 返回做 JSON 校验与兜底（宽容解析、默认值），失败时回退到“仅用
   placeName 直接作城市猜测”，保证接口不崩。
5. 把解析结果写入 Zustand（mapStore 扩展出 resolved 字段：城市+suburbs）。
6. 简单验证：手工对一个已知坐标（如悉尼 CBD）调用接口，确认返回合理的城市与 suburb。

【约束】
- 大模型调用做成可配置（env 配 model/api），不写死密钥。
- suburb 数据注入要注意 token 与相关度，先按城市做本地粗筛再给 LLM。
- 输出必须是结构化可机读，且带置信度，方便前端提示用户“系统判断你在 XX”。

【验收标准】
- `/api/resolve-location` 存在，输入坐标返回结构化 {mainCity, suburbs,…}。
- 解析结果写入 Zustand；对已知坐标能返回合理结果。
- LLM 异常/无返回时接口仍能给出兜底结果。
```

```

在 Web 页面以列表/卡片展示，并**默认过滤掉要求 PR 的职位**。

【具体步骤】

## 🧩 Prompt G — AI 筛选 + Chatbot 聊天交互（Copilot Kit）

```
【全局上下文】<粘贴/引用上方的“全局项目上下文”>

【任务目标】
用 Copilot Kit 实现 Chatbot 式 AI 筛选：把 F 阶段拿到的结构化职位数据喂给 AI，
用户用自然语言提问/筛选（如“选悉尼适合会计的、不要求 PR 的公司”“推荐这家公司的理由”），
AI 挑选并总结出合适的企业，以对话方式呈现。

【具体步骤】
1. 后端接入 Copilot Kit runtime：按 CopilotKit 官方方式提供 LLM 后端/或对接现有大模型，
   挂一个可对话的 agent（记住项目用的语言模型与 key 走环境变量）。
2. 定义可被 AI 调用的工具（前端 useCopilotAction / 后端 tools），例如：
   - `search_jobs(city, suburbs, keyword, allowPR=false)`
   - `filter_jobs(条件)` / `get_job_detail(jobId)` / `summarize_companies(list)`
   让 AI 能真正抓到最新职位，而不是只靠上下文里塞的静态数据。
3. 上下文注入：调用时把当前筛选结果（职位列表/已选公司）作为上下文给 AI，让对话基于真实数据。
4. 前端聊天组件 `components/chat/JobCopilot.tsx`（用 CopilotKit 的 useCopilotChat / 输入区）：
   用户输入自然语言 → AI 返回挑选出的合适企业 + 推荐理由，并可在对话卡片里直接展示职位/公司摘要。
5. 引导话术：给 AI 设定 prompt（system），要求它“默认优先不要求 PR、结合用户所在城市/suburb、
   给出明确推荐理由、一次别给太多、可追问细化”。
6. 把 AI 认可的企业/职位落进 Zustand（如 chatStore / 收藏）方便后续导出。

【约束】
- CopilotKit 版本与 Next.js 匹配，React 组件接入遵循其 API。
- Chat 里的 AI 行为要可配置（system prompt 放到配置/常量，方便调整）。
